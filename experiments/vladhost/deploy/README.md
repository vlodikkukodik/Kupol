# Деплой Vladhost на VPS

VPS `37.153.70.33` (Ubuntu 24.04). Панель: https://app.vladinc.ru. Сайты: `https://{site}.{user}.vladinc.ru`.

## Обновление

```bash
SSHPASS='…' ./deploy/deploy.sh      # или без SSHPASS, если настроен ssh-ключ
```

Скрипт собирает бинарь и фронтенд, заливает их и запускает `install-remote.sh`: подмена бинаря и фронтенда одним
`rename`, перезапуск службы, проверка `nginx -t` (при провале свои конфиги откатываются, чужие не затрагиваются),
проверка `/api/healthz`. Миграции БД применяются при старте службы.

## Первичная установка (уже сделана)

1. `deploy/prepare.sh` на сервере: swap 4 ГБ, пользователь `vladhost`, каталоги, БД и роль `vladhost`, `/etc/vladhost/env`.
2. `deploy.sh` (nginx подключит только http-часть, пока нет сертификата панели).
3. Сертификат панели:
   `certbot certonly --webroot -w /var/www/vladhost-acme -d app.vladinc.ru --cert-name app.vladinc.ru --deploy-hook "systemctl reload nginx"`
4. `deploy.sh` ещё раз — включится https-часть.
5. Администратор: `runuser -u vladhost -- bash -c 'set -a; . /etc/vladhost/env; VLADHOST_ADMIN_PASSWORD=… /opt/vladhost/bin/vladhost admin create --email … --username …'`

## Как устроены сертификаты сайтов

Панель работает без root и сама certbot запустить не может.

1. Создание сайта → панель кладёт пустой файл `/var/lib/vladhost/certs/queue/issue-{host}`.
2. `vladhost-certs.path` замечает файл → `vladhost-certs.service` запускает `/usr/local/lib/vladhost/certs.sh` (root).
3. Скрипт проверяет имя строгим шаблоном, выпускает сертификат (`certbot certonly --webroot`) и пишет результат
   в `/var/lib/vladhost/certs/status/{host}` (`ok` или `error: …`). Каталог `status` принадлежит root — панель
   не может подложить симлинк.
4. deploy-hook certbot (`cert-hook.sh`) копирует сертификат в `/etc/vladhost/certs/{host}`: воркеры nginx (www-data)
   не читают `/etc/letsencrypt/live`, где ключи других проектов. Тот же hook срабатывает при каждом продлении.
5. nginx берёт сертификат по SNI (`ssl_certificate /etc/vladhost/certs/$ssl_server_name/…`) — перезагрузка не нужна.
6. Панель раз в 5 секунд читает `status` и обновляет `sites.cert_status`. Заявка без ответа 30 минут → `failed`,
   пользователь может нажать «Повторить».

Удаление сайта → заявка `delete-{host}` → `certbot delete` и удаление копии.

## Веб-шлюз сайтов

Сайты пользователей отдаёт не nginx, а служба `vladhost-web` (`vladhost web`, `127.0.0.1:8091`): она понимает `.htaccess`
и сама показывает страницы «пустой сайт», 403, 404 и другие ошибки (их нет в папке пользователя). nginx держит TLS,
сжатие и показывает `/opt/vladhost/pages/__vh_down.html`, если шлюз недоступен. Служба работает под пользователем
`vladhost-web` без доступа к БД и секретам (`ProtectSystem=strict`, `InaccessiblePaths=/etc/vladhost …`, `MemoryMax=384M`).

```bash
systemctl status vladhost-web        # состояние
journalctl -u vladhost-web -f        # журнал
curl -s -H 'Host: blog.john.vladinc.ru' http://127.0.0.1:8091/   # проверка в обход nginx
```

Список поддерживаемых директив `.htaccess` и защиты — в `plan.md`, §16.

## Почта: подтверждение адреса, сброс пароля, уведомления

Письма уходят через SMTP-сервер, заданный в `/etc/vladhost/env` (например, `smtp.majordomo.ru`). Пока `VLADHOST_SMTP_HOST` и
`VLADHOST_SMTP_FROM` не заданы, почта выключена: панель работает, но подтверждения адреса, сброса пароля и уведомлений нет
(страница «Забыли пароль?» честно об этом скажет).

```bash
# дописать в /etc/vladhost/env (права файла 0640 root:vladhost остаются)
VLADHOST_SMTP_HOST=smtp.majordomo.ru
VLADHOST_SMTP_PORT=587            # 587 + starttls (по умолчанию) или 465 + VLADHOST_SMTP_TLS=tls
VLADHOST_SMTP_USER=noreply@vladinc.ru
VLADHOST_SMTP_PASSWORD=...        # пароль почтового ящика отправителя
VLADHOST_SMTP_FROM=noreply@vladinc.ru
systemctl restart vladhost
sudo -u vladhost env $(cat /etc/vladhost/env | xargs) /opt/vladhost/bin/vladhost mail-test --to вы@example.com   # проверка реквизитов
```

Шифрование обязательно: без STARTTLS/TLS пароль по сети не отправляется (режим `none` разрешён только для локального сервера).
Чтобы письма не попадали в спам, у домена отправителя нужны SPF-запись с сервером почты хостинга и подпись DKIM — это настраивается
в почте Majordomo (раздел «Домены → DNS»/почта), не в панели.
Письма ставятся в очередь (`mail_outbox`) и уходят фоновой службой с повторами при сбоях (1 мин, 5 мин, 30 мин, 2 ч, 6 ч, всего 6
попыток); после отправки тела писем (в них ссылки) стираются, записи о доставке хранятся 30 суток. Ссылки из писем одноразовые,
в БД лежат только их хеши (подтверждение — 48 часов, сброс пароля — 1 час); письма одного вида одному пользователю — не чаще раза
в минуту и не больше пяти в час. Уведомления (сертификат не выпущен или скоро истекает, диск заполнен на 90%) проверяются раз в 30
минут и отправляются один раз на событие только на подтверждённый адрес и только тем, кто их не отключил в «Настройках».

## Раздел SSL: сроки и перевыпуск

Панель показывает издателя, срок и имена сертификата адреса сайта, поддоменов и своих доменов. Сведения пишет root-скрипт
`cert-info.sh` в `/var/lib/vladhost/certs/info/{имя}` (строки `key=value`): его вызывают хук certbot (после выпуска и каждого
продления), выпускатель и выкладка (`install-remote.sh` запускает `cert-info.sh --all` для сертификатов, выпущенных раньше).
Панель читает только этот каталог, сами сертификаты ей недоступны. Кнопка «Перевыпустить» кладёт заявку `renew-{имя}`:
`certs.sh` вызывает certbot с `--force-renewal`; при неудаче действующий сертификат остаётся на месте, а панель оставляет имя
рабочим и показывает причину. Вручную можно не чаще раза в 72 часа на имя (лимиты Let's Encrypt общие на весь сервер).
Автопродление делает `certbot.timer` за 30 дней до срока; если к 14 дням до окончания оно не сработало, сводка аккаунта предупреждает.

```bash
ls /var/lib/vladhost/certs/info/            # сведения по именам
cat /var/lib/vladhost/certs/info/blog.user.vladinc.ru
```

## Настройки сайта

Раздел «Настройки» в кабинете сайта пишет `{каталог сайтов}/{адрес сайта}/settings.json` (рядом с `public/`, пользователь до него не
дотянется ни по FTP, ни через файловый менеджер). Шлюз читает файл без БД и перечитывает его при изменении (по времени и размеру),
всё прочитанное проходит `sitecfg.Sanitize`. Что настраивается: корневая папка (`root_dir`, например `dist`), индексные файлы,
листинг каталогов, страницы ошибок по кодам, редирект `www` (только на имя, которое обслуживается этим же сайтом) и HSTS
(`max-age` 6 месяцев, без `includeSubDomains`). Директивы `.htaccess` (`DirectoryIndex`, `Options`, `ErrorDocument`) сильнее.
HTTP всегда перенаправляется на HTTPS на уровне nginx, отдельной настройки для этого нет. Имена с собственной папкой (см. ниже)
корневую папку из настроек не используют. Шаги на сервере не нужны.

## Поддомены сайта и папки

Кроме адреса сайта (`blog.user.vladinc.ru`) у сайта бывают поддомены `{метка}.blog.user.vladinc.ru` (до 5 на сайт, до 10 на аккаунт).
DNS для них не нужен: `*.vladinc.ru` уже указывает на сервер. Сертификат выпускается по тому же пути, что для адреса сайта
(`certs.sh`, общий nginx-блок с regex `^(?:[a-z0-9-]+\.)?{сайт}.{пользователь}.vladinc.ru$`), поэтому **каждый поддомен — отдельный
сертификат, а лимит Let's Encrypt (50 в неделю) общий на весь vladinc.ru**. И поддомен, и свой домен можно привязать к папке сайта:
в файле привязки `/data/vladhost/domains/{имя}` первая строка — адрес сайта, вторая (если есть) — папка. Шлюз открывает её через
`os.Root` и считает корнем; поддомен обслуживается только своим сайтом, что бы ни лежало в файле привязки.
После обновления шаблонов nginx (`deploy.sh` ставит их сам) нужен `nginx -t && systemctl reload nginx`, если перезагрузка не выполнилась.

## Дополнительные FTP-аккаунты

У сайта кроме основного FTP-доступа (логин `blog.user`) может быть до 5 дополнительных аккаунтов: логин `{имя}.{сайт}.{пользователь}`,
свой пароль (хранится bcrypt, показывается один раз), ограничение подпапкой сайта и режим «только чтение». Таблица `ftp_accounts`
(миграция 0006). Смена пароля, режима, папки, отключение и удаление аккаунта закрывают его открытые сессии; основной доступ и другие
аккаунты это не затрагивает. Квота диска общая на сайт. Шаги на сервере не нужны, кроме обычной выкладки (миграция применяется при старте панели).

## Журналы сайтов

Шлюз пишет два журнала на каждый сайт в `/var/log/vladhost/sites/{адрес сайта}/`: `access.log` (каждый запрос) и `error.log`
(404, 403, 405 и прочие отказы), по одной JSON-строке на событие. Файл вращается при 4 МБ, хранятся 3 копии (`.1`–`.3`),
то есть не больше ~16 МБ на сайт и вид журнала. Раз в час шлюз удаляет журналы сайтов, которых больше нет.
Каталог принадлежит `vladhost-web:vladhost` с `setgid` (2750): панель читает через группу, остальные пользователи сервера доступа не имеют.
Панель показывает журналы в кабинете сайта (раздел «Журналы»): фильтр по классу ответа, поиск, постраничная подгрузка, скачивание.

```bash
ls -l /var/log/vladhost/sites/          # каталоги сайтов
tail -f /var/log/vladhost/sites/blog.user.vladinc.ru/access.log
```

## Статистика сайтов

Шлюз считает суточные счётчики (запросы, боты, просмотры страниц, уникальные посетители, популярные страницы, источники переходов,
классы ответов, трафик; сутки по UTC) и раз в 30 секунд и при остановке сохраняет их в `/var/log/vladhost/sites/{адрес}/stats.json`.
Хранится 90 суток. IP посетителей на диск не пишутся: для «уникальных» откладываются усечённые хеши с солью сайта, только за текущие
сутки. Панель показывает их в разделе «Статистика» кабинета сайта. Служба получает SIGTERM и успевает сохранить счётчики при перезапуске.

## Свои домены

Пользователь направляет A-запись домена на IP сервера; панель проверяет DNS, выпускатель создаёт
`/etc/nginx/vladhost-domains/{домен}.conf` и сертификат. Привязка домена к сайту — файл `/data/vladhost/domains/{домен}`.
Настройки: `VLADHOST_SERVER_IPS` и `VLADHOST_DOMAINS_DIR` в `/etc/vladhost/env`, `SERVER_IPS` в `/etc/vladhost/certs.conf`
(`deploy/prepare.sh` создаёт их; при необходимости `VLADHOST_SERVER_IP=… bash prepare.sh`).

```bash
ls /etc/nginx/vladhost-domains/          # server-блоки своих доменов
journalctl -u vladhost-certs -n 50       # выпуск/удаление
make test-deploy                         # тест скриптов на подменённых certbot/nginx (локально)
```

Подробности и защита — `plan.md`, §17.

## FTP

Встроенный FTP-сервер панели: `ftp.vladinc.ru:2121`, принимает FTPS (явный TLS, рекомендуется) и обычный FTP без шифрования (`VLADHOST_FTP_ALLOW_PLAIN=false` оставит только FTPS), пассивный режим, порты данных 50000–50100
(порт 21 занят стоковым proftpd, который мы не трогаем). Логин — `slug.username`, пароль отдельный на сайт.

- Сертификат `ftp.vladinc.ru` выпускается certbot'ом (webroot); deploy-hook `cert-hook.sh` кладёт копию в
  `/etc/vladhost/ftp/` (читает только группа vladhost). Сервер перечитывает файлы при смене, перезапуск не нужен.
- Если FTP не смог стартовать (нет сертификата, порт занят), панель работает дальше, в логе `ВНИМАНИЕ: FTP отключён`,
  в интерфейсе FTP показывается как недоступный.
- Переменные: `VLADHOST_FTP_ADDR`, `_HOST`, `_PUBLIC_IP`, `_PASSIVE_PORTS`, `_CERT`, `_KEY` (`deploy/prepare.sh` дописывает их в `/etc/vladhost/env`).
- Проверка с клиента: `lftp -u blog.имя,пароль -e "set ftp:ssl-force true" ftp.vladinc.ru:2121`.
- Открытые FTP-сессии не видят подмену каталога при деплое zip: запись в момент деплоя может уйти в старую версию.

## Базы данных (PostgreSQL, MariaDB, Adminer)

Раздел «Базы данных»: до 3 баз каждой СУБД на аккаунт, до 100 МБ на базу (сверх лимита база замораживается: чтение и удаление
данных, запись выключена, на почту приходит письмо; когда данные удалены и база стала заметно меньше лимита, запись
возвращается сама). Логин и имя базы — `{пользователь}_{имя}`, пароль виден один раз при создании.

- Подготовка сервера: `deploy/prepare-db.sh` (идемпотентна; от root на VPS). Ставит **отдельный** кластер PostgreSQL 16 `vladhost`
  (порт 5433, свой пользователь ОС `vhdb`, основной PostgreSQL на 5432 не трогается), MariaDB (порт 3306), PHP-FPM с отдельным
  пулом и Adminer 4.17.1 (контрольная сумма закреплена), сертификат `db.vladinc.ru` и ограничения памяти systemd (по 512 МБ на СУБД).
  Переменные `VLADHOST_DB_*` дописываются в `/etc/vladhost/env`; панель подхватывает их при следующей выкладке.
- Внешний доступ — только по TLS и только с IP из списка базы (в PostgreSQL — файлы `hba.d/db{id}.conf` с `hostssl`, в MariaDB —
  учётные записи на каждый адрес с `REQUIRE SSL`). Сертификат один на всё: `cert-hook.sh` раскладывает копии для `vhdb` и `mysql`.
- Веб-клиент: `https://db.vladinc.ru`. Кнопка «Открыть в Adminer» выдаёт одноразовую ссылку (2 минуты); `index.php` меняет токен на
  временную учётную запись (`POST /api/internal/db-session` на 127.0.0.1 с секретом `VLADHOST_DB_INTERNAL_KEY`) и пускает Adminer только
  к нашим двум серверам. Снаружи `/api/internal/` закрыт в nginx.
- Проверка после выкладки — только curl: `curl -sI https://db.vladinc.ru/`; `ss -ltn | grep -E ':(3306|5433)'`.

## Планировщик задач (cron)

Раздел «Планировщик»: до 5 задач на аккаунт, не чаще раза в 5 минут, предел 60 с на запуск, в журнале 50 последних запусков.
Расписание — пять полей cron по UTC. Два вида задач:

- **Запрос по адресу** (GET): работает всегда, внутри панели. Защита от обращения во внутреннюю сеть стоит на самом соединении (адрес
  проверяется после разрешения имени и при каждом редиректе), поэтому и подмена DNS её не обходит.
- **Команда в папке сайта**: панель без прав выполнять ничего не может и кладёт заявку в `/var/lib/vladhost/cron/queue`; по её появлению
  `vladhost-cron.path` запускает `cron-run.sh` от root. Он проверяет заявку и запускает команду в песочнице `systemd-run`: пользователь
  `vladhost`, видна только папка одного сайта (`/data/vladhost/site`, остальные сайты, `/etc/vladhost`, `/opt`, `/var/lib/vladhost` закрыты),
  без loopback и внутренних сетей, память 256 МБ, 64 процесса, 50% CPU, тайм-аут. Вывод до 32 КБ возвращается в журнал.
- Подготовка сервера: `deploy/prepare-cron.sh` (идемпотентна). Без неё HTTP-задачи работают, команды в интерфейсе недоступны.
- После трёх неудач подряд на почту приходит письмо (один раз на серию).
- Тест исполнителя на заглушке systemd-run: `make test-deploy`.

## Среды выполнения (PHP, Node.js, Python)

Раздел «Среда» в кабинете сайта: статика, PHP (8.2, 8.3, 8.4) или приложение на Node.js / Python. Работает для основного адреса
сайта и своих доменов без папки; поддомены и домены, привязанные к папке, остаются статикой.

- **Как идёт запрос.** nginx → веб-шлюз (`vladhost-web`) → для PHP: FastCGI к пулу сайта (`/run/vhphp/vhs{ID}.sock`), для приложений:
  обратный прокси на `127.0.0.1:{порт}`. Шлюз остаётся единой точкой: `.htaccess` (в том числе RewriteRule на `index.php`), журналы,
  статистика и страницы ошибок работают одинаково для всех сред. Файл настроек `runtime.json` лежит рядом с `public` (не в папке
  пользователя) и проходит проверку в шлюзе.
- **Подготовка сервера:** `deploy/prepare-runtime.sh` (идемпотентна, от root). Ставит `acl`, репозиторий Ondřej Surý и PHP-FPM 8.2/8.3/8.4
  с типичными расширениями, отключает стандартный пул `www` (переименовывает в `.vladhost-disabled`), включает `vladhost-runtime.path`
  (заявки от панели), `vladhost-runtime-perms.timer` (права каждые 15 секунд) и правила nftables для пользователей сайтов. Node.js и Python
  берутся установленные в системе. Файл `/var/lib/vladhost/runtime/caps` говорит панели, что доступно; `VLADHOST_RUNTIME_DIR` в env.
- **Изоляция.** У сайта свой системный пользователь `vhs{ID}` (uid 60000+ID) и свой пул PHP-FPM: `open_basedir` только папка сайта, свои
  `tmp`, сессии и журнал ошибок, `exec`/`system`/`proc_open` и подобные отключены, память 192 МБ, до 4 процессов, 60 секунд.
  Приложение — служба `vhapp-{ID}.service` в песочнице systemd (свои `public` и `tmp`, остальные сайты и секреты панели скрыты, память
  256 МБ, 64 процесса, 50% CPU). Пользователи сайтов не ходят на loopback, кроме баз (3306, 5433), портов приложений и DNS, и во
  внутренние сети (`deploy/nft/vladhost-rt.nft`, отдельная таблица `inet vladhost_rt`).
- **Права на файлы.** Файлы создают панель/FTP (`vladhost`) и приложение (`vhs{ID}`): доступ обоим и шлюзу выдан по ACL, остальным закрыт.
  Маска ACL у файлов зависит от прав при создании, поэтому раз в 15 секунд `runtime.sh perms-all` выравнивает её (внутри песочницы, где виден
  только этот сайт); перед деплоем и удалением сайта это делается сразу. Пока не прошло 15 секунд, панель может не суметь удалить
  каталог, только что созданный PHP.
- **Панель без прав** ничего не настраивает сама: заявки (`action=apply|stop|restart|status|logs|perms|purge`) кладутся в
  `/var/lib/vladhost/runtime/queue`, `deploy/bin/runtime.sh` проверяет их по строгим шаблонам и отвечает в `results/`. Тест на заглушках:
  `make test-deploy`.
- **Зависимости** (`npm install`, `pip install`, сборка) выполняются командой в «Планировщике» (песочница задач, `vladhost`, доступ в интернет).
- Проверка на сервере: `systemctl status vladhost-runtime.path`, `ls /run/vhphp`, `journalctl -u vhapp-{ID}`; проверка PHP-пула напрямую:
  `SCRIPT_NAME=/x.php SCRIPT_FILENAME=/путь/x.php REQUEST_METHOD=GET cgi-fcgi -bind -connect /run/vhphp/vhs{ID}.sock`.

## Установка приложений (WordPress в один клик)

Раздел «Приложения» в кабинете сайта: панель сама создаёт базу MariaDB, скачивает дистрибутив, раскладывает файлы, пишет `wp-config.php`,
выполняет установку WordPress и показывает логин и пароль администратора (один раз). Нужны среды выполнения и MariaDB (`prepare-runtime.sh`,
`prepare-db.sh`); раздел появляется сам, когда они есть. Сайт до установки должен быть пустым.

- Подготовка сервера: `deploy/prepare-cms.sh` (каталог кэша `/data/vladhost/cache/cms`, `VLADHOST_CMS_CACHE_DIR`, `VLADHOST_GATEWAY_URL`).
- **Дистрибутив.** Версия и sha256 закреплены в каталоге (`backend/internal/cms/catalog.go`, обновление версии — правка одной записи или
  `VLADHOST_CMS_CATALOG` с JSON-файлом). Архив скачивается с `downloads.wordpress.org`, сумма проверяется всегда, в том числе у кэша.
- **Ход установки** (7 шагов, в интерфейсе виден каждый): PHP включается сам (самая новая версия) → база `wp{номер сайта}` → скачивание →
  файлы (`Deploy`) → `wp-config.php` (случайные ключи и префикс таблиц, `FS_METHOD=direct`, `WP_HOME`/`WP_SITEURL` на https, `WPLANG`) →
  установка через веб-шлюз (`/wp-admin/install.php`, для не английского языка сначала шаг 1 с языковым пакетом) → проверка (сайт открывается).
  Любая ошибка откатывает базу и файлы: установку можно повторить.
- **Пароли** показываются один раз: после первого чтения итога они стираются из памяти панели. Забытый пароль администратора — по почте
  на странице входа WordPress.
- Проверено на сервере с настоящим WordPress 7.1.2: под пулом PHP-FPM сайта, с MariaDB через сокет, `open_basedir` и отключёнными
  `exec`/`system`; установка создаёт 12 таблиц, страница входа работает, языковой пакет качается.

## SSH и веб-терминал

Раздел «SSH-ключи» (аккаунт) и «Терминал» (кабинет сайта): вход по SSH ключом и терминал в браузере. Оболочка каждого сайта работает в закрытой
песочнице под отдельным системным пользователем `vhs{ID}` (uid 60000+ID).

- **Устройство.** Панель сама принимает SSH на порту **2222** (системный sshd на 22 не трогается; `VLADHOST_SSH_ADDR`, ключ сервера в
  `/data/vladhost/ssh/host_ed25519`, создаётся при первом запуске). Вход — только по ключам аккаунта, логин `сайт.пользователь` (как у FTP):
  `ssh blog.vlad@ssh.vladinc.ru -p 2222`. Пароли, пересылка портов, агент и X11 выключены; после 10 неудач с адреса он блокируется на 10 минут.
  Работают оболочка, команды (`ssh … 'cmd'`, поэтому scp, rsync и git по SSH), `sftp`.
- **Посредник оболочек** (`vladhost-shell.service`, `vladhost shell-broker`, от root): панель не имеет прав запускать процессы под другими пользователями,
  поэтому просит посредника по unix-сокету `/run/vladhost/shell.sock` (группа vladhost, 0660; посредник дополнительно проверяет uid клиента по
  SO_PEERCRED). Он проверяет запрос по метке `/var/lib/vladhost/runtime/shell/{id}` (её ставит исполнитель сред при включении доступа: `runtime.sh
  shell-on`) и запускает `systemd-run --pty` с песочницей: видна только папка сайта, `/etc/vladhost`, `/opt`, чужие сайты закрыты, память 512 МБ,
  128 процессов, сеанс до 8 часов, внутренние сети и loopback закрыты правилами nftables (`inet vladhost_rt`).
- **Включение доступа** — переключатель на странице «Терминал» сайта: исполнитель заводит пользователя, tmp и права (те же ACL, что у сред
  выполнения, поэтому файлы, созданные в оболочке, доступны панели и FTP), выключение закрывает открытые сеансы. Максимум 3 сеанса на сайт.
- **Ключи.** До 10 на аккаунт; ed25519, ECDSA или RSA от 2048 бит, без параметров `authorized_keys`. «Создать пару» делает ключ ed25519 в панели:
  закрытая часть показывается один раз и нигде не хранится. Один ключ — один аккаунт.
- **Веб-терминал**: xterm.js по WebSocket `/api/terminal/ws`; вход подтверждает одноразовый билет на 30 секунд (WebSocket из браузера не может передать
  заголовок Authorization), Origin проверяется. nginx: отдельный `location /api/terminal/` без буферизации и с часовыми таймаутами.
- Подготовка сервера: `deploy/prepare-ssh.sh` (после выкладки: нужен бинарь с `shell-broker` и `prepare-runtime.sh`). Ставит git, rsync, sftp-server,
  службу-посредника и переменные `VLADHOST_SSH_ADDR`, `VLADHOST_SSH_HOST`, `VLADHOST_SHELL_SOCKET`.
- Проверено на сервере с настоящим systemd-run: оболочка с PTY под `vhs{ID}` видит только папку сайта, `/etc/vladhost/env` недоступен, ps показывает один процесс, loopback закрыт, интернет
  работает, git/node/python/php на месте, размер окна и коды выхода передаются, `sftp-server` отвечает.
- Проверка на сервере: `systemctl status vladhost-shell`, `ss -ltn | grep 2222`, `journalctl -u vladhost-shell -f`.

## Журнал действий аккаунта

Раздел «Журнал действий» (аккаунт): что и когда делали в аккаунте, с какого адреса и из какой программы. Серверной подготовки не требует (миграция 0019 применяется при запуске панели).

- **Что пишется.** Входы, выходы, неудачные попытки входа (тому, чей аккаунт пробовали открыть; ответ пользователю при этом не зависит от того, есть ли такой аккаунт), регистрация, смена и сброс пароля, подтверждение адреса,
  настройки профиля, инвайты; создание и удаление сайтов, деплой архивом, правки файлов, настройки, домены, FTP (включение, аккаунты, пароли, **входы по FTP**), копии и их скачивание, сертификаты, среды,
  приложения, cron, базы, почта, DNS, SSH-ключи, доступ к оболочке и терминал. Отдельная запись у каждого события: время, вид, объект (сайт, домен, база…), адрес клиента, программа клиента (до 200 знаков).
- **Как пишется.** Слой `audit` в `httpapi` записывает успешные (< 400) изменяющие запросы вошедшего пользователя по таблице «метод + маршрут → событие» (`auditKinds` в `httpapi/activity.go`); отклонённые запросы
  не пишутся. Маршрут, которого нет в таблице, но который меняет данные, попадёт как «Другое действие» с шаблоном маршрута, так что новые возможности не выпадают из журнала. Имя сайта определяется до обработчика
  (у удалённого сайта его уже не найти); домены, базы и зоны называет сам обработчик (`setAuditTarget`). Чтения не пишутся, кроме скачивания копий и архива сайта. Сбой записи журнала не ломает запрос.
- **Слияние.** Частые однотипные события (правки файлов сайта, неудачные входы, соединения FTP) с одним пользователем, объектом и адресом в окне 10 минут складываются в одну строку со счётчиком и временем последнего.
- **Адрес клиента** берётся из `X-Forwarded-For` только от nginx на этой же машине (доверенный прокси 127.0.0.1); заголовок от постороннего клиента адрес не подменяет (проверено тестом).
- **Хранение.** 180 дней и не больше 5000 строк на пользователя; чистка раз в час. Своё событие видит только сам пользователь (`GET /api/activity`, страницы по курсору, фильтр по виду: безопасность, сайты, доступ, службы).
- **Не входит.** Просмотр журнала администратором по чужому аккаунту (аудит — пункт 25 плана), список активных сессий (пункт 19). Неудачные входы по FTP не пишутся: по логину сайта нельзя надёжно определить владельца.

## Поддержка и справка

Разделы «Поддержка» и «Справка» есть всегда: серверной подготовки не требуют (только миграция 0018, её применяет панель при запуске).

- **Обращения.** Пользователь пишет тикет (тема 3–120 знаков, раздел, текст до 5000 знаков) и ведёт переписку; статусы: «ждёт ответа» (поддержка ещё не ответила), «есть ответ», «закрыто».
  Ответ поддержки переводит тикет в «есть ответ», сообщение пользователя (в том числе в закрытый тикет) — обратно в «ждёт ответа». Пределы: 5 незакрытых тикетов на пользователя, 100 сообщений в тикете,
  20 сообщений пользователя в час. Пользователь не видит, какой именно администратор ответил («Поддержка»).
- **Кто отвечает.** Любой пользователь с ролью администратора: в разделе «Поддержка» у него вкладка «Все обращения» (очередь с фильтром по статусу и поиском по теме, имени и email). На пункте меню «Поддержка»
  показан значок: у пользователя — число тикетов с ответом, у администратора — число ждущих ответа.
- **Письма** (нужна настроенная исходящая почта панели, см. раздел «Почта: подтверждение адреса…»): администраторам — о новом обращении и о новом сообщении пользователя, пользователю — об ответе поддержки.
  Получают только те, кто подтвердил адрес и не отключил уведомления в «Настройках»; письма идут через очередь `mail_outbox` на языке получателя.
- **Справка.** Статьи — markdown-файлы `frontend/src/help/ru/*.md` и `frontend/src/help/it/*.md` (одно имя файла — одна статья на обоих языках), собираются в панель при сборке фронтенда. Формат: заголовок
  `--- title/category/description ---` и текст с заголовками `##`, списками, блоками кода, заметками `>`, ссылками `[текст](/адрес)`. Разметка разбирается собственным безопасным разбором без `v-html`.
  Тест `articles.test.ts` следит, чтобы набор статей на языках совпадал, ссылки вели на существующие страницы панели, а в итальянских текстах не было кириллицы. Чтобы добавить статью: два файла с одним именем
  и, если нужен новый раздел, ключи `help.categories.*` в `ru.ts` и `it.ts`.
- Проверка после выкладки: `curl -s https://app.vladinc.ru/api/tickets/summary` без токена отвечает 401 (раздел подключён), в панели — вход, «Справка», «Поддержка».

## Собственный DNS (ns.vladinc.ru и ns2.vladinc.ru)

Раздел «DNS» (аккаунт): зона своего домена, записи A, AAAA, CNAME, MX, TXT, SRV и CAA, проверка делегирования. Зону можно завести только для своего домена, подключённого
к одному из сайтов пользователя (тип «свой домен»; домены под `vladinc.ru` не принимаются); новая зона сразу получает A-запись на IP сервера и `www` (CNAME). Лимиты: 5 зон
на аккаунт, 100 записей в зоне.

- **Как это работает.** Оба имени (`ns.vladinc.ru` и `ns2.vladinc.ru`) указывают на один IP — сервер, где стоит панель; на нём уже работает BIND (стандартный пакет Ubuntu).
  Клиент у регистратора домена указывает эти два имени в NS-записях. Зоны хранит панель (`dns_zones`, `dns_records`) и отдаёт серверу файлом `/var/lib/vladhost/runtime/dns/state.json`;
  исполнитель (`runtime.sh dns-sync`, скрипт `dns-sync.py` от root) строго проверяет файл, собирает `/var/lib/bind/vladhost/{домен}.zone`, проверяет каждую зону `named-checkzone`,
  пишет перечень зон `/etc/bind/named.conf.vladhost` (подключён из `named.conf.local` одной строкой) и перечитывает BIND (`rndc reconfig` / `rndc reload {зона}`). Серийный номер SOA
  растёт при каждом изменении; SOA и NS создаёт скрипт, пользователь их не правит. Синхронизация повторяется сама (раз в минуту), если сервер не ответил; без зон стартовой синхронизации нет.
- **Что проверяется:** типы и значения записей (IPv4/IPv6 в каноническом виде, имена без пробелов и `..`, CNAME не на вершине зоны и не рядом с другими записями, MX и SRV с приоритетом,
  допустимые TTL, длина TXT до 2048 знаков с нарезкой на строки по 255 байт) — те же правила и в панели, и в `dns-sync.py` (сервер не верит панели).
- **Делегирование** (кнопка «Проверить делегирование»): NS-записи домена в публичном DNS сравниваются с нашими; состояния: `ok` (только наши), `partial` (только один наш),
  `mixed` (наши и чужие), `none`, `unknown` (сбой проверки).
- **Почта и DNS.** Если у домена есть зона и он делегирован на наши серверы имён, в разделе «Почта» появляется кнопка «Настроить DNS автоматически»: MX, SPF, DKIM и DMARC ставятся
  в зону одним действием (прежние MX и записи SPF/DKIM/DMARC заменяются, остальные записи не трогаются; поставленные записи помечены «почта»). Без зоны или без делегирования кнопки нет,
  вместо неё — подсказка, что сделать.
- **Безопасность BIND** (`prepare-dns.sh`): рекурсия и кэш только для самого сервера (публичный сервер имён не должен быть открытым резолвером), `rate-limit` ответов, версия скрыта, передача
  зон и динамические обновления запрещены. Сам сервер использует резолверы хостера, а не свой BIND. Прежние настройки сохраняются в `/root/vladhost-dns-backup/` (`rollback-dns.sh`).
- **Порядок:** `prepare-dns.sh` (после выкладки) → у регистратора клиента NS на `ns.vladinc.ru` и `ns2.vladinc.ru`. Имена `ns` и `ns2` в зоне `vladinc.ru` уже указывают на сервер (общая запись
  `*.vladinc.ru`); если регистратор клиента требует «glue» для имён под чужим доменом, это не нужно: серверы имён находятся вне зоны клиента.
- Проверка на сервере: `dig +short @127.0.0.1 SOA пример.ru`, `named-checkconf`, `rndc status`, `ls /var/lib/bind/vladhost`, `journalctl -u named -n 50`; снаружи — `dig @37.153.70.33 пример.ru NS` (порт 53 по UDP и TCP).
- Ограничения: один IP у обоих серверов имён (при его недоступности пропадают оба), вторичных серверов и DNSSEC нет, свои NS-записи для поддоменов (делегирование дальше) не поддерживаются.

## Почта на своих доменах

Раздел «Почта» (аккаунт): ящики вида `info@ваш-домен.ru`, алиасы и пересылки, общий ящик домена (`*`), автоответчик, пересылка с копией или без,
журнал доставки и webmail. Домен должен быть подключён к одному из сайтов пользователя (тип «свой домен»); домены под `vladinc.ru` не принимаются.
Лимиты: 5 доменов, 10 ящиков, 20 алиасов на аккаунт, ящик 50–2000 МБ.

**Порядок подготовки сервера** (после выкладки; каждый скрипт делает копию и умеет откатиться): `prepare-mail.sh` → `prepare-mailfilter.sh` → `prepare-webmail.sh`.

- **Устройство.** Принимает и отправляет exim4 (шаблон `deploy/mail/exim4.conf`; в EHLO — `mail.vladinc.ru`, он же PTR и сертификат), ящики хранит dovecot
  (`deploy/mail/dovecot-99-vladhost.conf`, Maildir в `/var/vmail/{домен}/{ящик}`, пользователь vmail, uid 5000, квоты, IMAP 993, POP3 995, ManageSieve 4190).
  Доставка в ящик идёт по LMTP, вход в SMTP (465 и 587) — только по TLS через dovecot. Сертификат `mail.vladinc.ru` выпускает certbot, копию для dovecot кладёт `cert-hook.sh`.
- **Панель — источник правды.** Она пишет `/var/lib/vladhost/runtime/mail/state.json` (домены, ящики с хешами `SHA512-CRYPT`, алиасы, ключи DKIM, правила ящиков,
  список на удаление) и просит исполнителя `runtime.sh mail-sync`; `mail-sync.py` строго проверяет файл и раскладывает `/etc/vladhost/mail/{domains,mailboxes,
  aliases,dovecot-users,dkim/}`, создаёт папки ящиков, скрипты sieve и безопасно удаляет ушедшие (символьные ссылки не разыменовываются). Пароли в открытом виде
  нигде не хранятся: сгенерированный показывается один раз. Если сервер не ответил, изменение уже сохранено, а панель повторяет синхронизацию сама (раз в минуту);
  без единого домена стартовая синхронизация не запускается.
- **DNS.** Для каждого домена панель показывает MX, SPF, DKIM (селектор `vh1`, RSA 2048) и DMARC и проверяет их по запросу («Проверить DNS»).
- **Доставляемость.**
  * **SRS:** письма, которые сервер пересылает дальше по алиасу (redirect-роутер exim), уходят с конвертным отправителем `SRS0=…@mail.vladinc.ru`, иначе получатель отклоняет их
    по SPF исходного отправителя; уведомления о недоставке возвращаются автору (`vladhost_srs`). Пересылка ящика (sieve `redirect`) идёт от адреса самого ящика
    (`sieve_redirect_envelope_from = recipient`): SPF и DKIM его домена действуют, а SRS не нужен. Секрет — `/etc/vladhost/mail/srs_secret`, создаётся один раз и менять его нельзя.
    SRS не решает проблему DMARC со строгой политикой (`p=reject`) у исходного домена: для этого нужен ARC, его в сборке exim нет.
  * Нужно у хостера и регистратора: PTR-запись IP на `mail.vladinc.ru`, открытые порты 25, 465, 587, 993, 995 и 4190 (у многих хостеров порт 25 закрыт), SPF-запись
    `v=spf1 ip4:<IP> -all` у `mail.vladinc.ru`. Перед первой рассылкой стоит проверить IP по чёрным спискам.
- **Спам и вирусы** (`prepare-mailfilter.sh`): rspamd (SPF, DKIM, DMARC, содержимое, самообучение) со своим Redis на сокете `/run/vladhost-redis/redis.sock`
  (Redis соседних проектов не используется) и ClamAV (clamd + freshclam, без удвоения памяти при обновлении базы). Оценка rspamd от 6 — заголовок `X-Spam: Yes`
  и письмо попадает в «Спам» (общее правило sieve `before.d/10-spam.sieve`; заголовки `X-Spam` извне отбрасываются), от 15 — отказ в SMTP-сессии; вирус — отказ. Письма своих клиентов
  (с паролем) и приложений сервера не проверяются. Если rspamd или clamd не отвечают, письмо не теряется и проходит без проверки (причина в журнале exim). Пользователь
  обучает фильтр сам: письмо перенесли в «Спам» — это спам, вынесли из «Спама» (не в корзину) — не спам (dovecot imapsieve → `rspamc learn_*`). ClamAV занимает около
  1 ГБ памяти: проверьте `free -m` после установки. Если CDN ClamAV отказывает серверу в загрузке базы (бывает лимит «cool-down» на сутки), `prepare-mailfilter.sh` не падает:
  письма идут без проверки на вирусы, а таймер `vladhost-clamd-ready` сам запустит clamd, когда freshclam скачает базу.
- **Автоответчик и пересылка** (окно «Изменить» у ящика): панель превращает их в `~/sieve-panel/panel.sieve` (vacation с датами и периодом, `redirect` с копией или без). Личные
  правила фильтрации пользователь ведёт в Roundcube или любой программе с ManageSieve (порт 4190); свой автоответчик Roundcube выключен, чтобы он не спорил с панельным.
  Спам не пересылается и не получает автоответа (общее правило выполняется раньше).
- **Журнал доставки** (карточка домена): `runtime.sh mail-log` запускает `mail-log.py`, который читает журнал exim (`/var/log/exim4/mainlog`, при необходимости и предыдущий)
  и очередь `exim4 -bpr` и отдаёт события домена: принято, доставлено, отложено, не доставлено, отклонено. Клиент видит только письма своего домена.
- **Заполнение ящика:** раз в цикл уведомлений панель шлёт владельцу письмо при заполнении ящика на 90 % (повторно — только после падения ниже 80 %).
- **Webmail** (`prepare-webmail.sh`): Roundcube 1.7.4 (закреплён по sha256) на `https://webmail.vladinc.ru`, отдельный пул PHP-FPM `vhwebmail` (php 8.3, open_basedir),
  база SQLite в `/var/lib/vhwebmail`, вход по адресу и паролю ящика (IMAP/SMTP/ManageSieve через `mail.vladinc.ru` с проверкой сертификата), плагины archive, zipdownload,
  managesieve, markasjunk. Смена пароля — только в панели (Roundcube не знает хеши). Откат: `rollback-webmail.sh`. Адрес webmail панель берёт из `VLADHOST_WEBMAIL_URL`.
- **Защита от злоупотреблений:** отправитель обязан быть из домена своего ящика, не больше 300 писем в час с ящика, подмена адресов чужих доменов запрещена.
- **Резервные копии и откат:** `prepare-mail.sh` сохраняет прежние настройки exim и dovecot в `/root/vladhost-mail-backup/` (`rollback.sh`); `prepare-mailfilter.sh` — `rollback-filters.sh`
  (останавливает rspamd, ClamAV и Redis; почта продолжает идти без проверки); `prepare-webmail.sh` — `rollback-webmail.sh`.
- **Не входит:** ARC (для пересылок с DMARC `p=reject`), списки рассылки, общие папки. При удалении аккаунта панели строки в БД удаляются, а папки ящиков на диске
  остаются — их убирает оператор.
- Проверка на сервере: `exim4 -bV`, `doveconf -n | head`, `ss -ltn | grep -E ':(25|465|587|993|995|4190)'`, `tail /var/log/exim4/mainlog`, `rspamc stat`,
  `systemctl status rspamd clamav-daemon vladhost-redis`, `free -m`.

## Известные ограничения

- Лимит Let's Encrypt: 50 сертификатов в неделю на домен `vladinc.ru` (общий с другими проектами сервера).
  Сейчас прикрыт лимитом «1 сайт на аккаунт» и регистрацией по инвайтам.
- Сайты пользователей живут на соседних поддоменах основного домена. От подброса cookie защищает префикс
  `__Host-` у refresh-cookie, от запросов к панели с чужих страниц — проверка `Origin`. Полная изоляция
  потребовала бы отдельного домена для сайтов или записи в Public Suffix List.
- Стоковый proftpd на порту 21 принимает системных пользователей по паролю без TLS — это не Vladhost, но стоит
  решить, нужен ли он вообще (после отключения FTP панель можно перевести на порт 21).
- Вход на сервер по паролю root; лучше перейти на ключ и отключить парольный вход.
